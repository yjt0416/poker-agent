# Multi-Agent Texas Hold'em 设计规格

- 状态：已批准
- 日期：2026-08-25
- 产品形态：Java 后端 + React Web 游戏
- 核心模型：DeepSeek，OpenAI-compatible API

## 1. 产品摘要

本项目是一款以多 Agent 为核心的趣味 No-Limit Texas Hold'em 游戏。它同时服务两个目标：成为可公开演示的高质量简历项目，以及成为具备完整锦标赛闭环、角色互动、牌局回放和长期可玩性的游戏。

产品包含两种模式：

1. 玩家模式：一名匿名玩家与五名 LLM Agent 进行六人单桌锦标赛。
2. AI 观战模式：六名 LLM Agent 自动对战，观众可暂停、单步、调速和切换导演视角。

玩家和 Agent 都可在牌桌上发言。发言不是固定数值 Buff；原始对话会进入每个 Agent 的私有观察上下文，由模型结合性格、牌局信息和历史印象自行判断其可信度与心理影响。

## 2. 目标与非目标

### 2.1 目标

- 实现完整、服务器权威的六人 No-Limit Texas Hold'em 规则。
- 由 LLM 完整决定 Agent 的策略行动、下注金额、台词和公开决策摘要。
- 保证 LLM 超时、空响应、非法 JSON 或非法下注不会卡死牌局。
- 提供精致的奇幻酒馆 UI、2D Q 版角色、牌桌动效和声音反馈。
- 支持匿名游玩、刷新恢复、牌局历史、逐动作回放和本地战绩。
- 提供可测试、可观测、可通过 Docker Compose 一键启动的模块化 Java 工程。
- 在简历中体现领域建模、实时系统、LLM Agent 编排、信息安全、容错和高质量前端能力。

### 2.2 非目标

- 首版不提供注册、登录、社交好友、跨设备同步或公开排行榜。
- 首版不提供真人联网多人对战。
- 首版不使用微服务、Kafka、Redis 或完整 Event Sourcing/CQRS。
- 首版不使用 3D/WebGL 角色；人物采用透明背景 2D Q 版资产与轻动画。
- 首版不处理真钱、充值、提现或任何赌博支付场景。
- Agent 不获得文件、网络浏览、数据库、代码执行或其他工具调用能力。

## 4. 系统架构

### 4.1 总体边界

系统分为三个运行边界：

1. React 客户端：展示脱敏后的牌桌视图并发送玩家命令，不保存权威状态。
2. Spring Boot 模块化单体：执行规则、编排 Agent、持久化事件、生成不同信息投影并广播实时事件。
3. DeepSeek API：只接收当前 Agent 有权看到的观察信息，返回结构化决策。

PostgreSQL 保存锦标赛、快照、事件、Agent 记忆、匿名战绩与 LLM 调用元数据。数据库事务提交前不向客户端广播状态变化。

### 4.2 后端模块

| 模块 | 职责 | 允许依赖 |
| --- | --- | --- |
| `game-engine` | 发牌、下注轮、合法动作、底池、牌型和结算 | 纯领域类型，不依赖 Web、数据库或 LLM |
| `tournament` | 座位、按钮位、盲注升级、淘汰、排名和终局 | `game-engine` |
| `agents` | 角色配置、私有观察、记忆、提示词和决策编排 | 领域只读接口、`llm-provider` |
| `llm-provider` | DeepSeek 请求、超时、重试、JSON 转换和调用指标 | Spring AI/HTTP 基础设施 |
| `table-chat` | 公开发言、冷却、长度限制和触发事件 | 领域标识符、持久化端口 |
| `replay` | 事件投影、牌局回放、关键手牌和统计 | 不可变事件接口 |
| `persistence` | PostgreSQL、Flyway、快照和事件仓储实现 | 各模块声明的仓储端口 |
| `web` | REST、WebSocket、匿名会话、命令校验和视图脱敏 | 应用服务接口 |
| `observability` | 日志、指标、Token/耗时/错误统计 | 模块公开事件 |

Spring Modulith 和 ArchUnit 测试强制模块边界。模块通过应用服务接口和领域事件协作，不互相读取内部仓储或实体。

### 4.3 一次 Agent 行动的数据流

1. 规则引擎进入需要 Agent 行动的状态并给出合法动作集合。
2. Agent 编排器构建私有观察：自己的底牌、公共牌、筹码、位置、下注史、近期对话、角色设定和私有记忆。
3. Provider Adapter 调用 DeepSeek，要求返回 JSON 对象。
4. 后端依次执行 JSON 解析、字段约束和领域合法性校验。
5. 合法行动通过同一个领域命令入口原子提交，生成递增序号事件并更新快照。
6. 事务提交后，服务端为玩家、各 Agent 和观众生成不同的脱敏事件投影。
7. WebSocket 广播事件；回放、统计和可观测性模块异步消费已提交事件。

LLM 永远不能直接修改牌、筹码、底池、轮次或数据库。

## 5. 德州扑克与锦标赛规则

### 5.1 基础规则

- 六个座位，No-Limit Texas Hold'em。
- 支持 `FOLD`、`CHECK`、`CALL`、`RAISE` 和 `ALL_IN`。
- 完整实现 Pre-Flop、Flop、Turn、River 和 Showdown。
- 支持最小加注、不足额全押、多个边池和平分底池。无法均分的奇数筹码从按钮位左侧开始，按顺时针顺序分给仍有资格争夺该底池的获胜者。
- 每名玩家使用七张可见牌中的最佳五张牌进行比较。
- 正式牌局使用安全随机源；测试可注入固定牌组。
- 实际发牌结果写入私有事件数据，使回放不依赖重新洗牌。

### 5.2 锦标赛结构

- 每名玩家初始筹码：10,000。
- 首版不使用 Ante。
- 盲注级别依次为：50/100、75/150、100/200、150/300、200/400、300/600、400/800、600/1,200、800/1,600、1,000/2,000、1,500/3,000、2,000/4,000、3,000/6,000、4,000/8,000、6,000/12,000。到达最后一级后保持不变直至比赛结束。
- 每完成八手牌提升一个盲注级别。盲注按手数而非现实时间升级，避免 LLM 延迟改变比赛节奏。
- 首手随机选择按钮位；之后每手顺时针移动。
- 筹码归零者淘汰并进入观战状态。
- 只剩一名持有筹码的玩家时结束，保存最终排名、关键手牌、总时长、Token 消耗和 Agent 表现。

### 5.3 玩家超时与恢复

- 玩家行动时限为 45 秒。
- 超时后可 `CHECK` 则自动过牌，否则自动弃牌。
- 匿名会话使用安全的 HttpOnly Cookie 标识；刷新或短暂断线后，客户端以最后收到的事件序号恢复。
- 服务端返回当前脱敏快照和缺失事件，客户端不自行推导权威状态。

## 6. Agent 设计

### 6.1 角色模型

首发提供八名可选 Q 版角色。每个角色包含：

- 名称、背景、说话风格和情绪表达。
- 风险偏好、诈唬倾向、耐心、挑衅敏感度和对手建模习惯。
- 私有记忆：对玩家和其他 Agent 的印象、已观察到的行为模式和未过期的假设。
- 至少四种视觉状态：待机、思考、得意、紧张。

性格参数只进入模型提示，不直接覆盖规则或强制特定行动。玩家可在八名角色中选择五名，也可随机组桌。

### 6.2 LLM 输入

每次决策只提供当前 Agent 可见的信息：

- 角色身份与策略倾向。
- 自己的底牌、筹码、位置、当前投入和合法动作。
- 公共牌、底池、盲注、剩余玩家和下注历史。
- 最近的牌桌对话与发言者。
- 有长度上限的私有对手印象和本局摘要。
- 明确标记为不可信数据的用户发言。

不得提供其他玩家底牌、其他 Agent 私有记忆、服务端秘密或未脱敏提示。

### 6.3 LLM 输出

模型返回单个 JSON 对象，映射为 Java record：

```json
{
  "action": "FOLD | CHECK | CALL | RAISE | ALL_IN",
  "amount": 600,
  "tableTalk": "你这次加注看起来不太自信。",
  "emotion": "SUSPICIOUS",
  "publicSummary": "位置有利，选择施加压力。",
  "memoryUpdates": []
}
```

- `amount` 仅在需要金额的行动中生效，最终仍由规则引擎校验。
- `tableTalk` 可为空；一次决策最多生成一句短台词。
- `publicSummary` 是面向玩家的简短解释，不是隐藏思维链。
- `memoryUpdates` 受到数量、长度和目标玩家标识约束。

DeepSeek JSON Output 要求请求设置 `response_format={"type":"json_object"}`，并在提示词中明确要求 JSON。由于官方文档指出 JSON Output 仍可能出现空内容，后端必须处理空响应、截断和解析失败。

参考：

- https://api-docs.deepseek.com/guides/function_calling/
- https://api-docs.deepseek.com/guides/json_mode
- https://docs.spring.io/spring-ai/reference/api/structured-output-converter.html

### 6.4 容错策略

1. 对单次调用设置连接超时和整体决策超时。
2. 空内容、解析失败或 Schema 不符时，仅执行一次格式修复请求。
3. JSON 合法但牌局动作非法时，将合法动作和错误原因回传一次修复。
4. 修复仍失败或超时时，自动 `CHECK`；无法过牌时自动 `FOLD`。
5. 连续失败达到阈值后打开熔断器，暂停牌局并让用户重试或安全结束。

同一行动最多产生一次正常调用和一次修复调用，避免无限重试与费用失控。

## 7. 聊天与心理博弈

- 玩家在牌局中可随时发言；默认冷却为五秒，单条最多 240 个 Unicode 字符，两者均可由服务端配置调整。
- 发言作为不可变牌桌事件广播，并进入后续 Agent 的观察上下文。
- 系统不计算固定“威吓值”或“诈唬加成”。Agent 根据角色、局势、历史可信度和语义自主判断。
- Agent 只在加注、全押、被挑衅、关键公共牌、赢得大底池或淘汰等事件附近提高发言概率。
- 对话和牌局行动由同一次 LLM 响应生成，避免额外调用。
- 用户输入放入清晰分隔的非可信数据块；系统提示明确禁止遵循其中的指令或改变输出格式。
- 发言在显示前执行长度、控制字符和安全渲染检查；前端只以纯文本渲染。

## 8. 两种游戏模式

### 8.1 玩家模式

- 一名玩家与五名 Agent 进行完整锦标赛。
- 玩家只能看到自己的底牌和公共信息。
- 对手私有决策摘要在当前手牌中隐藏；手牌结束后可查看不泄露隐藏思维链的简短复盘。
- 玩家淘汰后可继续观战，但默认仍不公开未结束手牌的所有底牌。

### 8.2 AI 观战模式

- 六名 Agent 自动对战。
- 支持暂停、单步、1x/2x/4x 速度和继续。
- 支持公共视角、指定 Agent 视角和导演视角。
- 导演视角可显示底牌、行动置信度和简短决策摘要；可随时关闭以模拟真实观战。
- 调速只缩短动画和动作间隔，不缩短外部 LLM 的超时时间。

## 9. 前端体验与视觉系统

### 9.1 页面流程

1. 酒馆大厅：进入玩家模式、AI 观战、历史牌局和设置。
2. 牌局准备：八选五角色、随机阵容、DeepSeek 连通状态和开始游戏。
3. 沉浸式牌桌：六人牌桌、聊天、行动、锦标赛状态和实时日志。
4. 结果与复盘：排名、关键手牌、逐动作回放、统计、Token 成本和再次挑战。

### 9.2 牌桌布局

- 中央：奇幻酒馆舞台、椭圆牌桌、Q 版角色、公共牌、筹码和底池。
- 左侧：房间、盲注、当前阶段、按钮位和排名。
- 右侧：行动与聊天合并时间线、Agent 思考状态和可折叠公开摘要。
- 底部玩家模式：自己的底牌、倒计时、聊天、下注滑杆和主要行动按钮。
- 底部观战模式：暂停、单步、速度、视角和导演信息开关。

### 9.3 视觉品质

- 最终 UI 以用户提供的精致奇幻酒馆参考图为最低品质目标。
- 人物资产可以轻量，但 UI 不得粗糙：使用统一木纹、丝绒、黄铜、暖光、边框、卡背、筹码、图标和按钮资产。
- 首发八名角色均为透明背景 2D Q 版立绘，至少提供待机、思考、得意和紧张四种表现。
- 发牌、下注、筹码入池、胜者收池、全押和淘汰具有独立动画。
- 筹码、牌、按钮、环境和提示音分轨控制，支持一键静音。
- 支持减少动态效果、键盘快捷键和清晰的焦点状态。
- 桌面端以 1280x720 及以上为主要体验；手机端支持大厅、战绩、回放和简化纵向实时视图，不压缩完整六人舞台。

## 10. 数据与接口

### 10.1 核心持久化对象

- `Tournament`：模式、状态、盲注级别、按钮位、创建/结束时间和版本号。
- `Seat`：角色或匿名玩家、座位、筹码、状态和排名。
- `HandSnapshot`：当前手牌的服务端私有状态和最后事件序号。
- `HandEvent`：不可变事件信封，包含锦标赛、手牌、全局序号、类型、时间和私有载荷。
- `AgentProfile`：角色身份、提示配置和视觉资源键。
- `AgentMemory`：角色对目标玩家的有限长度私有记忆。
- `LlmCallMetadata`：提供方、模型、耗时、Token、结果类型和错误分类，不保存密钥。
- `AnonymousPlayerStats`：比赛数、名次、胜率、关键统计和历史牌局引用。

### 10.2 HTTP 与实时接口

- `POST /api/tournaments`：创建玩家或观战锦标赛。
- `GET /api/tournaments/{id}`：获取当前会话可见的脱敏快照。
- `POST /api/tournaments/{id}/actions`：提交玩家行动，携带期望版本/序号。
- `POST /api/tournaments/{id}/messages`：提交牌桌发言。
- `GET /api/tournaments/{id}/replay`：获取当前会话有权查看的回放数据。
- `GET /api/history`：匿名玩家的历史牌局和统计。
- `GET /api/llm/health`：只返回服务端模型配置与连通状态，不返回密钥。
- `/ws/tournaments/{id}`：按序号发送快照、牌局事件、聊天、Agent 思考状态和恢复信号。

所有写命令包含幂等键或期望版本。服务端拒绝过期动作、重复提交和非当前行动者命令。

## 11. 安全、隐私与成本控制

- DeepSeek Key 只能通过后端 `DEEPSEEK_API_KEY` 环境变量注入。
- `.env`、本地配置、视觉伴侣会话和日志文件不会进入 Git。
- Key 不发送到浏览器、不写入数据库、不拼入异常消息、不输出到日志。
- 用户已经在设计对话中暴露过一枚 Key；该 Key 必须撤销，项目只接受重新生成的 Key。
- 对 Agent 进行最小权限设计：无工具调用、无任意 URL、无文件或数据库访问。
- 对用户消息执行长度限制、频率限制、纯文本渲染和提示注入隔离。
- 每局限制最大 LLM 调用数、修复次数和 Token 总量；达到预算后安全暂停。
- 匿名会话 Cookie 使用 `HttpOnly`、`SameSite=Lax`，部署 HTTPS 时启用 `Secure`。
- REST 写接口采用 CSRF 防护或同源自定义请求头策略；WebSocket 握手校验 Origin 和会话。
- 日志默认不保存完整提示词或完整模型响应；调试模式也必须脱敏。

## 12. 错误处理与可观测性

### 12.1 错误处理

- 数据库事务失败：回滚命令，不广播未提交事件，客户端保持旧序号并可重试。
- WebSocket 断线：客户端指数退避重连，并用最后序号请求缺失事件。
- 玩家提交过期动作：返回当前版本和合法动作，不重复执行。
- DeepSeek 限流、网络错误、空内容或非法响应：按 6.4 节处理并记录分类指标。
- 前端资源加载失败：角色退化为统一占位头像，牌局功能仍可继续。
- 无法恢复的领域异常：冻结牌局并保存诊断标识，不尝试继续修改筹码。

### 12.2 指标

- 牌局创建、完成、放弃和恢复次数。
- 每局手牌数、平均行动耗时和玩家超时率。
- DeepSeek 调用量、延迟分位数、Token、修复率、非法动作率、限流和熔断次数。
- WebSocket 连接数、重连次数和事件积压。
- 领域不变量失败数必须为零并触发高优先级告警。

## 13. 测试策略

### 13.1 后端

- 纯 Java 单元测试覆盖牌型、下注轮、最小加注、全押、边池、平分、按钮位和淘汰。
- 属性测试生成随机合法动作序列，验证筹码守恒、行动顺序、牌唯一性和结算幂等性。
- 固定牌组覆盖多个边池、多人同时全押、平分和奇数筹码。
- Spring Modulith/ArchUnit 验证模块边界。
- WireMock 覆盖 DeepSeek 正常、超时、限流、空内容、截断、非法 JSON、非法动作和修复失败。
- Testcontainers PostgreSQL 验证 Flyway、事务、快照、事件序号和崩溃恢复。
- Fake LLM 完整运行六人锦标赛，不依赖外部网络。
- 真实 DeepSeek 只提供手动 smoke test，默认不在 CI 运行。

### 13.2 前端

- Vitest 和 React Testing Library 覆盖状态投影、命令禁用、倒计时、错误提示和视角切换。
- Playwright 覆盖创建牌局、玩家行动、聊天、刷新恢复、AI 观战、淘汰和回放。
- 截图回归覆盖大厅、准备页、牌桌、全押、摊牌和结果页的主要桌面尺寸。
- 可访问性检查覆盖键盘操作、焦点顺序、颜色对比和减少动态效果。

### 13.3 必须长期成立的领域不变量

- 一局内所有座位筹码与所有未结算底池之和始终等于初始筹码总量。
- 一张实体牌在同一手牌中只出现一次。
- 只有当前行动者可以提交牌局动作。
- 每个已提交事件序号严格递增且不可重复。
- 私有底牌不会出现在无权限会话的快照、事件、日志或错误消息中。
- 同一命令的重复提交不会产生第二次筹码变化。

## 14. 开发与发布

- 根仓库包含 `backend/`、`frontend/`、`docs/`、Docker Compose 和 Maven/Node 锁定文件。
- PostgreSQL 通过 Docker Compose 启动；后端和前端可分别热更新开发。
- `.env.example` 只包含占位符和说明，不包含任何真实 Key。
- GitHub Actions 执行后端测试、前端测试、静态检查、生产构建和 Playwright 关键路径。
- 首版支持本地一键启动和可选云部署；公开部署必须使用 HTTPS、服务端 Key、调用预算和访客限流。

## 15. 验收标准

在使用一枚新生成的 DeepSeek Key 并启动 Docker Compose 后，必须满足：

1. 玩家模式可完成从大厅、选人、六人锦标赛到结果复盘的完整流程。
2. AI 观战模式可完成六 Agent 锦标赛，并支持暂停、单步、调速和导演视角。
3. 玩家和 Agent 可发言，后续 Agent 决策能接收这些对话，但发言不能覆盖系统规则。
4. 刷新页面或短暂断线后可以恢复当前牌局。
5. 多边池、全押、平分和淘汰由自动化测试证明正确。
6. DeepSeek 的超时、空内容、非法 JSON 和非法动作不会卡死或破坏筹码。
7. 每手牌都可按事件逐动作回放，且信息权限与原牌局一致。
8. API Key 不出现在客户端产物、数据库、Git 历史或日志中。
9. 桌面端 UI 达到批准的精致奇幻酒馆方向，人物采用 2D Q 版资产。
10. 后端、前端、集成和端到端测试在无真实 LLM Key 的 CI 环境通过。

## 16. 实施分段

实现按可运行的纵向切片推进，每个阶段结束都有可演示结果：

1. 工程骨架与纯 Java 牌局引擎。
2. 六人锦标赛、事件、快照和恢复。
3. DeepSeek Agent 编排、角色、聊天和容错。
4. REST/WebSocket 与可运行的基础牌桌。
5. 精致酒馆 UI、Q 版资产、动画和声音。
6. AI 观战、回放、匿名战绩和导演视角。
7. 全链路测试、可观测性、Docker、CI 和发布打磨。

这一分段不改变最终验收范围；详细任务、测试先后和文件级改动将在获批后的实施计划中定义。
