## 已复现问题

### P1：桌面日志撑高整张牌桌，操作区被裁切

在观战自动播放至第 3 手、版本 62 后暂停，切换 1440×900 视口。日志已累积至保留上限附近。浏览器 DOM 实测：

- `.game-layout` 高 782px；
- `.table-stage` 高约 3013px；
- `.right-panel` 高约 2977px；
- `.action-dock` 顶部位于约 3010px，超出窗口。

固定高度的 Grid 行被右侧内容的最小尺寸撑大，外层又裁切内容，导致牌桌和操作区无法正常显示。只给 `.log-list` 设置 `overflow:auto` 和 `min-height:0` 不足以限制父级 Grid 项。

位置：`frontend/src/styles.css:69`、`:70`、`:72`、`:105`。

建议：约束 Grid 行高度，例如 `grid-template-rows:minmax(0,1fr)`，允许侧栏项收缩并由日志区域独立滚动。回归验证 0/40 条日志、玩家/观战、桌面/短屏四类组合。

### P1：玩家淘汰后继续开牌报错

独立 HTTP 测试中，玩家第一手全下后筹码归零，状态为 `BETWEEN_HANDS`。随后调用 `/api/tables/current/next-hand` 返回 HTTP 400：`unknown player: PlayerId[...]`。

原因：下一手及其 Agent 行动已经推进，但结算或投影仍调用 `holeCards(table.humanId)`；已淘汰玩家不属于新手牌。该异常可能发生在状态写入之后。

位置：`backend/src/main/java/com/agenttavern/web/GameTableService.java:127`、`:207`、`:263`。

建议：显式建模玩家已淘汰状态；投影在玩家未参与当前手牌时返回空底牌；允许继续观战或重新开桌，不再显示玩家操作。增加“第一手淘汰→下一手→刷新”的接口回归测试。

### P1：多人全下结算丢失公共牌

浏览器中，玩家持 5♠、10♠，翻牌前投入 10,000，最终收到“旅人收下 30400 筹码”的结算，但公共牌仍是五张牌背，刷新后仍然如此。独立 HTTP 测试也观察到全下结算 `boardCount=0`。

原因：`recordSettlement` 接收的是执行最后一个动作之前的不可变 `Hand`，随后用它的 `board()` 保存最终牌面。该动作同时触发后续公共牌发出与结算时，新公共牌没有被保存。

位置：`backend/src/main/java/com/agenttavern/web/GameTableService.java:110`、`:182`、`:195`、`:205`。

建议：以已提交事件中的 `CommunityCardsDealt` 补齐最终公共牌，或保存明确的结算投影。结算应保留最终公共牌、各底池派奖及获胜牌型。无需公开未获授权的对手底牌。

### P2：快捷加注能选择非法金额，滑块值与提交值不一致

真实牌局的最小加注目标为 816，点击“2×”后主按钮变成“加注 300”，点击后显示“该行动当前不合法”。“3×”同样写死为 450。

同一场景点击“全下”后，主按钮显示 10000，原生滑块的可访问值却是 9966：以 816 为起点、步长 50 无法到达 10000。

位置：`frontend/src/App.tsx:411`、`:412`、`:413`。

建议：先定义倍数基准（大盲、当前下注或底池），再约束在服务端合法目标区间。文案改为“加注至”；提供精确数字输入，确保合法下限、上限及 all-in 能准确到达；操作等待期间禁用金额编辑。

### P2：手机布局遮挡公共牌和角色

390×844 视口下，豪哥与沈听澜重叠，左右角色遮挡公共牌，玩家手牌/名牌压住小满区域。缩小角色到 `scale(.68)` 没有解决绝对定位座位的空间冲突。

位置：`frontend/src/styles.css:134`、`:271`、`:287`。

建议：手机端采用独立座位布局和小头像名牌，优先保证五张公共牌、底池及操作按钮；角色立绘放到可展开详情。至少回归 390px、760px、1180px 两侧及桌面尺寸。

### P2：新牌桌残留旧发言，部分状态展示不准确

从已结束的玩家牌桌切换到全新观战牌桌时，新牌桌版本为 1、没有行动记录，气泡仍显示上一桌小满的发言。`hydrate` 在聊天和日志都为空时没有重置发言状态。

已淘汰角色也被统一渲染为“已弃牌”，无法区分本手退出和整场淘汰。

位置：`frontend/src/App.tsx` 的 `hydrate`；`frontend/src/components/AgentSeatView.tsx:18`。

建议：按 `tableId` 重置会话展示；分别显示已弃牌、全下、已淘汰和当前行动者。

## 代码审查发现的可靠性缺口

以下来自调用链和状态结构检查，未使用真实外部模型或数据库进行故障注入。

### P1：超时、重试与命令幂等没有贯通 HTTP 层

前端请求 10 秒超时；模型单次请求默认 20 秒、最多尝试两次；一次玩家动作又会同步推进多个 Agent。模型请求发生在牌桌锁内，读取当前状态也需要同一把锁。

前端超时只更新提示，没有读取最新状态。HTTP 动作只提交 `type/amount`，后端每次生成新 command UUID 并使用服务器当前版本。重试若恰逢玩家下一轮行动，可能被当成新动作；底层已有幂等机制并不能识别这种客户端重试。

位置：`frontend/src/api.ts:57`；`frontend/src/App.tsx:175`；`backend/src/main/java/com/agenttavern/web/PlayerActionRequest.java`；`GameTableService.java:103`、`:108`；`llmprovider/DeepSeekDecisionProvider.java:46`。

建议：客户端提交稳定的 `commandId` 和 `expectedVersion`；发生不确定结果时先同步权威状态。将模型推理移出长时间持锁区，按每桌串行任务调度，并通过轮询/SSE/WebSocket 给出已提交进度；不要仅提高超时阈值。

### P1：Web 会话恢复未接上已有持久化能力

`tables`、`sessions`、玩家显示名与身份映射、展示日志都在 `GameTableService` 的内存结构中。即使启用 PostgreSQL 保存锦标赛，Web 服务重启后旧 Cookie 仍无法定位原牌桌；前端对 401 会自动创建新桌。

位置：`backend/src/main/java/com/agenttavern/web/GameTableService.java:56`、`:57`、`:286`；`frontend/src/api.ts:91`。

建议：持久化会话与牌桌成员映射，以已存检查点和事件重建公开展示；区分无会话、会话过期、可恢复牌桌。补充 Web 层重启恢复验收，而不只重建领域命令服务。

### P2：锦标赛完成和模式切换缺少明确产品状态

`roundDone` 将 `BETWEEN_HANDS` 与 `COMPLETE` 合并，最终仍显示“开始下一手牌”，但后端仅允许前者。下一手按钮没有等待禁用。点击当前已选中的玩家/观战模式仍会调用创建新桌，替换当前会话。

位置：`frontend/src/App.tsx:265`、`:400`；`GameTableService.java:129`。

建议：区分手牌结算、玩家淘汰、锦标赛完成；展示最终排名及“再开一桌”。模式选择与新建牌桌分开；已选模式保持当前牌桌。对所有会产生命令的入口统一处理进行中状态。

### P2：长时间运行缺少资源回收

服务器会话与牌桌 Map 没有淘汰机制；Cookie 的 8 小时有效期不会自动删除服务端数据。本地存储每次提交复制累计事件和回执，持续建桌与长局会增加内存和复制成本。

位置：`GameTableService.java:56`；`backend/src/main/java/com/agenttavern/web/RuntimeTournamentStore.java`。

建议：加入会话过期与牌桌生命周期清理；本地模式只复制被修改的牌桌数据，使用有界展示历史和明确的持久化归档策略。

## 体验和工程优化

1. **先让信息可信。** “剩余 28 秒”“气氛 68%”“排名 #2”“豪哥连续两局加注”均为固定内容；接入真实计算前应去掉数值或明确标成示例。设置按钮没有行为，F/C/R 提示也没有对应键盘实现。
2. **突出 Agent 差异。** 在可见界面说明当前是本地决策还是模型决策，并保留简短的公开行动解释。把聊天历史与行动日志分别展示；当前真实发言成功后只替换气泡，行动日志不呈现该发言。
3. **改善反馈。** 显示 SB/BB、明确行动者、具体跟注金额和目标总投入；结算突出赢家、最终公共牌和派奖明细。移动端不能把错误提示随连接状态一起隐藏。
4. **收敛前端状态。** `App` 同时保存服务端快照与多份派生 state，还混有演示逻辑，容易出现旧气泡等残留。拆分连接/命令 hook、牌桌投影、下注控制和演示数据适配器。
5. **补真实状态测试。** 现有 App 测试主要验证演示状态，未覆盖合法金额边界、淘汰、比赛完成和长日志布局。优先给上述复现问题加回归，再建立最小浏览器端到端流程。
6. **统一启动入口。** 当前系统默认 Java 25，但项目严格要求 21；可提供仅对本进程生效的 Java 21 检测和双服务启动脚本。根目录 README 应指向实际可玩分支，避免启动错误版本。

## 建议实施顺序

先修桌面日志布局、淘汰后继续、全下结算牌面、加注合法性；随后处理手机布局与终局状态；再接通 HTTP 幂等、异步 Agent 推进和 Web 会话恢复。音效、动效和长期记忆应排在这些正确性与可用性问题之后。
